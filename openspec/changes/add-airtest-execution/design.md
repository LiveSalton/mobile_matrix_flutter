## Context

见 proposal.md - Why。现有 STF 控制面已建立设备会话和当前设备选择；Airtest 已可在当前 Mac 上通过 ADB 截图回退方式连接真机，但控制台未拥有调用它的受限接口。STF 仍是设备在线、占用和会话状态的唯一事实来源。

## Goals / Non-Goals

**Goals:**

- 为一台或多台 STF 可执行 Android 真机提供一个可观察、受限且真实调用 Airtest 的最小执行链路。
- 把已有的抖音 Airtest 任务及其模板资源纳入项目目录，通过任务注册表暴露给控制台。
- 每次任务为每台设备生成隔离的截图证据，执行结束后状态机回到可再次执行状态。
- 把 Airtest 运行时的就绪状态与控制台步骤和执行结果联动。
- 允许根启动脚本在隔离目录中准备可复现的 Airtest Python 环境。

**Non-Goals:**

- 不实现任意 Python、Airtest 脚本上传、任意路径执行、远程代码执行、批量编排、队列、定时任务或跨主机执行器。
- 不复制或持久化 STF 设备状态，不改变 STF 占用模型。
- 不支持 iOS/WDA、公网暴露或多租户鉴权。

## Decisions

### 受限动作 API

服务端提供引擎状态查询、任务目录查询、单设备兼容执行和多设备执行接口。执行接口只接受任务注册表中的任务标识；首版登记现有的 `douyin_follow_message` 任务，并保留 `capture` 作为健康检查任务。多设备请求逐台调用相同的受限执行器并聚合逐设备结果；服务端使用参数数组启动隔离 Python，不拼接 shell 命令，也不接收用户代码。

选择这一方式而不直接在浏览器调用 ADB，是因为浏览器无法可靠读取本机 USB 设备，且服务端可统一返回失败分类。选择动作枚举而不开放脚本输入，是为了保留本机可信环境的最小攻击面。

### 设备与运行时边界

执行前由服务端通过 ADB 二次确认每个目标有效，并以设备序列号连接 Airtest。工作台从 STF 实时设备流读取候选设备，只允许选择 `available` 与当前控制会话持有的 `using` 状态；后者是控制页已连接真机的正常 STF 状态，不等同于其他用户占用。服务端不信任客户端状态，逐台返回不可连接错误但继续处理其他目标。每次执行使用独立证据目录和唯一截图文件名，结果返回截图 API 地址。Airtest 任务统一使用 ADB 截屏与 ADB 触控回退参数，以避免依赖可能在真机上要求安装组件的 minicap/Yosemite 路径。

### 运行时准备

根启动脚本维护项目 `.runtime/airtest-venv` 隔离环境，并通过环境变量传入 STF。该目录为本机运行产物，不进入版本库。若用户设置运行时路径覆盖变量，脚本优先使用该路径。

### 控制台状态

控制台在设备控制会话成功后查询引擎状态：可用时启用动作选择与执行；不可用时显示服务端原因。执行请求完成后仅显示 API 返回的真实结果，不能以本地计时器模拟成功。

## Risks / Trade-offs

- [ADB 截屏回退性能较低] → 首版仅用于单设备、按需执行；后续再在独立变更中评估更高性能采集方案。
- [设备在点击执行前离线] → 服务端逐台二次校验并把连接异常映射为该设备的不可执行结果，不阻断其他目标。
- [Python 环境被移动或损坏] → 启动脚本检测并重建隔离环境；控制台显示不可用而非假设成功。
- [本机 API 被不受信任的网络访问] → 维持现有本机/可信内网边界，接口不接受任意代码或 shell 参数。

## Migration Plan

1. 启动脚本准备隔离 Airtest 环境并传递运行时路径。
2. 部署含 API 与工作台更新的 STF 构建产物后重启 Mobile Matrix。
3. 回退时移除 Airtest 环境变量并恢复上一版构建；`.runtime` 可安全删除并在下次启动时重建。
